Module 1 of 4 · Foundations

What a function really is

Build a correct mental model of functions before writing a single fancy one: definition vs. call, parameters vs. arguments, scope, and return values.

The core idea

A function is a named, reusable block of instructions that Python only runs when it is called. Writing def greet(): does not print or compute anything — it just teaches Python a new word. The work happens at greet().

basics.py
# defining does nothing yet
def greet(name):
    return f"Hello, {name}!"

# calling actually runs it
message = greet("Asha")
print(message)  # Hello, Asha!
Analogy — A function definition is a recipe card pinned to the fridge. Writing the recipe doesn't cook dinner. Only when someone actually follows it (calls it) with real ingredients (arguments) does a dish (return value) come out.

Parameters vs. arguments

name in the definition is a parameter — a placeholder. "Asha" at the call site is the argument — the real value filling that placeholder. People use the words interchangeably in conversation, but the distinction matters when reading Python's error messages.

Scope: where names live

Variables created inside a function are local — they exist only during that call and disappear afterward. Python looks up names using the LEGB rule: Local → Enclosing → Global → Built-in.

x = 10  # global

def tweak():
    x = 99  # local — a NEW variable, shadows the global one
    print("inside:", x)

tweak()
print("outside:", x)
# inside: 99
# outside: 10   -- global x untouched
Misconception — "Assigning to a variable inside a function changes the outer variable." False by default — assignment inside a function creates a local variable unless you explicitly declare global or nonlocal.

return vs. print

returnprint
Sends a value back to the caller so it can be used furtherDisplays text to the console; the function itself still returns None
Ends function execution immediatelyDoes not end the function
Used for computation and logicUsed for human-facing output/debugging
Exercise 1.1 — Fix the function

This function should return the square of a number so it can be reused elsewhere, but right now it only prints it. Rewrite it below.

def square(n):
    print(n * n)
def square(n):
    return n * n

result = square(5)   # result is now usable: 25

Key takeaways

  • Defining ≠ running. Nothing executes until the function is called.
  • Parameters are placeholders in the definition; arguments are real values at the call site.
  • Local variables live and die inside a single call, per the LEGB lookup order.
  • return hands data back for reuse; print just displays it.

Module 2 of 4 · Flexible Function Design

Parameters, arguments, and designing clean signatures

Go beyond the basics: default values, keyword arguments, *args/**kwargs, and why mutable defaults are a classic trap.

Default & keyword arguments

Defaults make parameters optional. Keyword arguments let callers pass values by name, in any order, which makes call sites self-documenting.

def book_ticket(city, date, seat="economy", meal=None):
    return f"{city} on {date}, {seat} seat, meal={meal}"

book_ticket("Delhi", "2026-08-01")                       # uses defaults
book_ticket(date="2026-08-01", city="Delhi", seat="business")  # keyword, any order

*args and **kwargs

*args collects any number of extra positional arguments into a tuple. **kwargs collects extra keyword arguments into a dictionary. Use them when a function genuinely needs to accept a variable amount of input.

def order_summary(customer, *items, **details):
    print(customer, items, details)

order_summary("Rae", "pen", "notebook", gift_wrap=True, express=False)
# Rae ('pen', 'notebook') {'gift_wrap': True, 'express': False}
Analogy — Think of a function signature like a restaurant order form. Required fields (positional args) must be filled. Fields with pre-printed defaults (default args) can be left as-is. A "notes" box that accepts anything extra is **kwargs — a flexible catch-all.
Misconception — "Mutable default arguments reset every call." They don't. def f(items=[]): creates the list once, at definition time, and reuses the same object across all calls — a notorious Python bug source.
Demonstration of the mutable-default trap
def add(item, bucket=[]): bucket.append(item) return bucket add("a") # ['a'] add("b") # ['a', 'b'] ← unexpected! same list reused

Fix it with bucket=None and create a fresh list inside the function when bucket is None.

Comparison: argument styles

StyleBest for
PositionalSmall, obvious argument lists (e.g. add(a, b))
KeywordMany parameters, improving call-site readability
*argsUnknown number of same-type positional inputs (e.g. sum_all(*numbers))
**kwargsPassing through flexible options/config to another function
Exercise 2.1 — Design a signature

Write a function make_profile(name, age, **extra) that returns a dictionary combining name, age, and any extra keyword fields. Try calling it with an email and a city.

def make_profile(name, age, **extra):
    profile = {"name": name, "age": age}
    profile.update(extra)
    return profile

make_profile("Rae", 29, email="rae@x.com", city="Pune")

Key takeaways

  • Default values make arguments optional; keyword arguments improve readability.
  • *args/**kwargs collect variable-length positional/keyword input.
  • Never use a mutable object (list, dict) as a default value — use None and build fresh inside.

Module 3 of 4 · Handling Errors Deliberately

try / except / else / finally

Errors are not failures of your code — they're events your code can plan for. Learn to catch the right exceptions, and only the right ones.

Anatomy of a traceback

When Python can't continue, it raises an exception — an object describing what went wrong — and prints a traceback showing the call chain that led there.

Traceback (most recent call last):
File "app.py", line 4, in <module> result = 10 / 0 ZeroDivisionError: division by zero

Read tracebacks bottom-up: the last line names the exception type and message; the lines above trace which call led there.

The four-part structure

try:
    value = int(user_input)
except ValueError as e:
    print(f"Not a number: {e}")
else:
    print("Parsed successfully:", value)  # runs only if no exception
finally:
    print("Done trying.")  # always runs, error or not

Catch specific exceptions, not everything

PatternVerdict
except ValueError:✅ Precise — you know exactly what you're handling
except (ValueError, TypeError):✅ Fine — handle multiple known cases together
except Exception:⚠️ Broad — use only at a top-level boundary, and log it
except: (bare)❌ Dangerous — silently swallows everything, including Ctrl+C and real bugs
Analogy — A bare except: is a smoke alarm you've disconnected because it kept beeping. You stop getting warned about anything — including the fire that actually matters.

Raising your own exceptions

def withdraw(balance, amount):
    if amount > balance:
        raise ValueError("Insufficient funds")
    return balance - amount

Raising early with a clear message ("fail fast") is far easier to debug than letting bad data silently propagate deeper into a program.

Misconception — "finally only runs if there's an error." It runs unconditionally — success, failure, or even a return inside the try block.

Key takeaways

  • Read tracebacks bottom-up: exception type + message first, then the call chain.
  • else runs only on success; finally always runs.
  • Catch specific exception types — bare except: hides real bugs.
  • Use raise to fail fast with a clear message instead of propagating bad data.

Module 4 of 4 · Mastery

Custom exceptions, decorators & context managers

Combine functions and error handling into production-grade patterns used in real Python codebases.

Custom exception classes

Subclass Exception to create domain-specific errors. This lets callers catch your errors specifically, without swallowing unrelated ones.

class InsufficientFundsError(Exception):
    def __init__(self, balance, amount):
        super().__init__(f"Tried to withdraw {amount}, only {balance} available")
        self.balance = balance
        self.amount = amount

def withdraw(balance, amount):
    if amount > balance:
        raise InsufficientFundsError(balance, amount)
    return balance - amount

Exception chaining

Use raise NewError(...) from original_error to preserve the original cause while raising a more meaningful, higher-level exception — common when wrapping low-level errors (e.g. network failures) into domain errors.

try:
    parse_config(file)
except FileNotFoundError as e:
    raise ConfigError("config missing") from e

Decorators: functions that wrap functions

A decorator takes a function and returns a new function that adds behavior — commonly used to retry on failure, log calls, or measure timing, without touching the original function's body.

def retry(times):
    def decorator(func):
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)
                except ConnectionError:
                    print(f"attempt {attempt+1} failed, retrying...")
            raise ConnectionError("all retries failed")
        return wrapper
    return decorator

@retry(times=3)
def fetch_data(url):
    ...
Analogy — A decorator is like a phone case: it doesn't change the phone inside, it wraps around it and adds protection (retry logic, logging) that activates automatically every time you use the phone.

Context managers: guaranteed cleanup

with statements guarantee that setup and teardown code run — even if an exception occurs in between. This is the modern replacement for manual try/finally cleanup around resources like files or connections.

with open("data.txt") as f:
    contents = f.read()
# file is automatically closed here, even if read() raised

Comparison: cleanup strategies

ApproachTrade-off
Manual try/finallyExplicit but verbose; easy to forget in new code paths
with context managerConcise, guaranteed cleanup, the idiomatic Python choice
No cleanup handlingResource leaks (open files, connections) under error conditions
Misconception — "Custom exceptions are overkill for small scripts." Even a two-function script benefits: catching InsufficientFundsError specifically is safer and clearer than guessing what a generic ValueError meant six months later.
Exercise 4.1 — Build a guarded resource pattern

Write a decorator @log_errors that wraps any function, catches any exception it raises, prints f"Error in {func.__name__}: {e}", and re-raises it.

def log_errors(func):
    def wrapper(*args, **kwargs):
        try:
            return func(*args, **kwargs)
        except Exception as e:
            print(f"Error in {func.__name__}: {e}")
            raise
    return wrapper

Key takeaways

  • Custom exception classes make error handling specific and self-documenting.
  • raise ... from ... preserves the original cause when wrapping errors.
  • Decorators add cross-cutting behavior (retries, logging) without modifying the original function.
  • with blocks guarantee cleanup runs, replacing manual try/finally for resources.

Final Practical Challenge

Build a resilient config loader

Combine everything: flexible function signatures, precise exception handling, a custom exception, and cleanup.

CHALLENGETask

Write a function load_setting(config, key, default=None, *, required=False) that:

  • Returns config[key] if present
  • Returns default if missing and required=False
  • Raises a custom MissingSettingError if missing and required=True
  • Uses try/except/else/finally to log every lookup attempt, success or failure
Your solution
class MissingSettingError(Exception):
    pass

def load_setting(config, key, default=None, *, required=False):
    try:
        value = config[key]
    except KeyError:
        print(f"[log] '{key}' not found")
        if required:
            raise MissingSettingError(f"'{key}' is required but missing")
        value = default
    else:
        print(f"[log] '{key}' found: {value}")
        return value
    finally:
        print(f"[log] lookup attempt finished for '{key}'")
    return value

Cheat sheet

Function syntax

def f(a, b=1, *args, **kwargs):
    return a

Error handling syntax

try:
    ...
except SpecificError as e:
    ...

    ...

Summary notes

  • Functions: definition ≠ execution; local scope by default; return over print for reusable results.
  • Design signatures with defaults and keyword args for readability; never mutable defaults.
  • *args/**kwargs for variable-length input.
  • Catch specific exceptions; use else for success-only code and finally for guaranteed cleanup.
  • Fail fast with raise; build custom exceptions for domain-specific clarity.
  • Decorators and with blocks are the idiomatic tools for cross-cutting concerns and cleanup.
